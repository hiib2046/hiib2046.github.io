이 챕터는 한 문장으로 모인다. **코드를 직접 쓰는 사람에서, 코드가 스스로 만들어지게 하는 시스템을 짜는 사람으로 바뀌라는 것.** 아래는 그걸 외우고 넘어갈 수 있게 추린 뼈대다. 🔑 표시는 그 항목을 기억에 박는 고리다.

## 왜 바이브 코딩이 끝났나

- 바이브 코딩의 정체 = **stateless chat(맥락이 매번 0에서 시작) + 수동 복붙.** 맥락 채우기도 옮기기도 다 사람 몫이라 오류가 폭발한다.
- 🔑 전형적 장면: 새벽 3시에 이해도 못 한 코드를 붙여넣고 잔다. 다음 날 왜 이런 코드가 있는지 본인도 모른다. 그래서 슈타인버거가 "이제 슬롭(slop, 저품질 결과물)"이라 못박았다.
- 카파시의 구분: 바이브 코딩 = **바닥 올리기**(누구나 코딩), 에이전틱 엔지니어링 = **천장 지키기**(프로 품질 유지). 대립이 아니라 방향이 다르다.
- '코딩'(글쓰기)이 아니라 '엔지니어링'(시스템 설계)인 이유: 산출물이 코드 조각이 아니라 동작하는 환경과 검증 루프 전체로 바뀌어서.
- 공식 정의 3요소 = **컨텍스트 · 검증 · 도구.** 이게 그대로 첫 세 기둥이 된다.

## Pillar 1. Context Engineering

컨텍스트를 정확히 필요한 만큼만 정밀하게 준다.

- **핵심 명제**: 출력 품질은 입력의 양이 아니라 정밀도에 비례한다. LLM은 확률 엔진이라 노이즈가 늘면 분산이 커지고 환각이 는다.
- Context is King은 맞지만, **dump everything(다 던지기)은 틀렸다.**
- 🔑 "AI가 변덕스럽다"의 진짜 원인 = 확률적 혼란(노이즈 낀 컨텍스트). 범인은 모델이 아니다.
- 두 단어: **Fresh**(오늘 유효한 것만) + **Condensed**(같은 정보를 더 짧게).
- 윈도우는 한계가 아니라 **버짓**이다. 통장에 200K 있어도 다 쓰지 않는다.
- Second Brain = 코드가 못 담는 '왜'를 리포에 저장. 3자산 = **PRD · Configuration · ADR.**
- 한 줄: **도메인 지식이 코드베이스에 없으면, 에이전트에겐 존재하지 않는 것이다.**

## Pillar 2. Agentic Validation

에이전트가 외부 신호로 스스로 검증하고 고친다.

- **절대 규칙**: 자기 평가는 절대 못 믿는다. 확률 엔진이 자기 답을 평가하면 같은 분포에 오염되니까.
- **신호는 모델 밖에서** 와야 한다: 컴파일러 · 테스트 · 브라우저 · 로그 같은 결정론적 시스템.
- **2레이어**: Pass/Fail(통과 · 실패) 위에 Observability(로그로 내부 상태 확인)를 쌓는다.
- 🔑 왜 2레이어냐: 결제 테스트는 통과했는데 금액이 **100배 청구**되는 버그. Pass/Fail로는 못 잡는다. LogQL로 내부 상태를 직접 묻는다.
- 한 줄: **크래시 없음은 약한 신호, 내부 상태가 정확함이 강한 신호.** 사고 나면 "AI 잘못"이 가장 틀린 답이다. 검증 환경을 안 깐 사람 잘못이다.

## Pillar 3. Agentic Tooling

사람을 부르는 멈춤(마찰)을 도구로 없앤다.

- 정의 = **마찰의 전략적 제거.** 감소가 아니라 제거다. 한 번 손보면 다시는 안 멈추게.
- 마찰(friction) = 인간 개입을 강제하는 모든 병목. "로그인해 주세요", "콘솔에서 봐 주세요" 하며 멈추는 순간.
- 🔑 원칙(슈타인버거): 에이전트가 못 하는 일에 도달하면, 대신 해주지 말고 **도구를 만들어라.** 물고기 말고 낚싯대를 줘라.
- CLI를 1차 다리로 두는 이유: 에이전트도 텍스트로 작동, 거의 모든 시스템이 제공, 조합 가능, 코드화 쉬움.
- 코드화 4패턴: **포털→CLI · 디플로이→스크립트 · 룩업→MCP · 승인→Policy.**
- 목표 = **디커플링.** 실행만 하면 되는 미들티어는 에이전트에게, 결정 · 트레이드오프는 사람에게.

## Pillar 4. Agentic Codebases

에이전트가 헷갈리지 않게 코드베이스를 다듬는다.

- 현실: **95%가 브라운필드**(오래 묵은 레거시). 이게 에이전틱 루프에 독을 푼다.
- 🔑 패턴 오염 = **같은 일 하는 패턴이 둘이면 틀린 걸 고를 확률 50%.** `src/billing/`과 `src/payments/`가 공존하면 신호가 없어 반반으로 갈린다.
- 골든 프린시플 = **Consistency over DRY**(일관성 위해 반복을 감수). 🔑 `formatPrice`가 50군데면 에이전트는 그 50군데를 다 컨텍스트로 끌어온다. 추상화가 오히려 비용. (단 논쟁 중, 인간 가독성엔 DRY가 여전히 유효)
- 4요소: 패턴 오염 제거 · 구조 일관성(디렉토리 · 네이밍 표준) · 에이전트용 로깅(JSON이라야 LogQL로 자기검증) · Golden Rules + RAG.
- 한 줄: **다음 사람이 읽을 코드가 아니라, 다음 에이전트가 실행할 코드를 쓴다.**

## Pillar 5. Compound Engineering

개인 도구를 팀 자산으로 쌓아 복리를 만든다.

- 🔑 산수: 한 명이 1시간 만든 도구를 17명이 쓰면 **18명분.** 도구 N개면 조합은 **N²**로 늘어 다항식 생산성.
- **곱셈 함정**(꼭 외울 것): 생산성 = 코드 일관성(IV) × 라이브러리 크기(V). 곱셈이라 한쪽이 0이면 결과도 0. 스킬 30개 쌓아도 브라운필드면 산출은 0에 수렴한다.
- 팀이 모을 4자산: **Shared Skills · MCP · CLAUDE.md · Golden Rules.**
- 90/10 규칙: 새 기능의 90%가 기존 자산 조합, 새로 짜는 코드는 10% 미만.

## 더하기가 아니라 곱하기

- 다섯 기둥은 레이어 케이크가 아니라 **격자(lattice)**다. 한 작업의 같은 순간에 동시에 맞물려 서로를 강화한다.
- 🔑 시나리오(Stripe→Adyen, 5000줄 · 호출처 30곳 · 1주): Day1 컨텍스트 + 툴링, Day2-3 코드베이스, Day4-5 검증 + 자산화. 좋은 팀은 다섯에 동시 투자해 출시 제품 수가 3배에서 5배로 는다.
- 역할 변화: 옛 아키텍트(코더 팀 관리자) → 새 아키텍트(**시스템 설계자**: 루프 설계 · 컨텍스트 관리 · 툴링 인프라).
- 격차는 매월 단위로 벌어져 **협곡**이 된다. 전환은 불가피하고 유일한 변수는 받아들이는 속도다.
- 결론 한 문장: **코드를 쓰는 것을 멈추고, 코드가 스스로를 만들 수 있게 하는 시스템을 엔지니어링하라.**
