월요일의 클로드와 수요일의 클로드는 같은 모델이다. 그런데 한쪽은 한 번에 끝내고, 다른 쪽은 엉뚱한 파일을 건드린 뒤 "다 됐습니다"라고 거짓 보고를 한다. 달랐던 건 모델이 아니라 그날의 작업 환경, 곧 하네스(harness)다. **모델은 우리가 못 바꾸지만 환경은 오늘 당장 바꿀 수 있다.** Ch 4는 그 환경을 설계하는 일(Harness Engineering)을 여섯 개의 축으로 풀어냈고, 이 글은 그 여섯을 한자리에 모은다.

## 왜 모델이 아니라 환경인가

- **통제권**: 모델은 매일 대여료를 내고 쓰는 블랙박스다. 환경은 우리가 만들고 고친다.
- **수치**: LangChain 팀은 모델과 프롬프트를 고정한 채 하네스(셀프 검증 루프, 자동 컨텍스트 수집)만 손봐 벤치마크를 14%p 올렸다. 모델 교체로 얻는 개선이 보통 몇 퍼센트인 걸 생각하면 큰 차이다.
- **진화**: 프롬프트 엔지니어링 → 컨텍스트 엔지니어링 → 하네스 엔지니어링. 실패했을 때 던지는 질문이 "프롬프트를 잘못 썼나"에서 "내 하네스의 어디가 비었나"로 바뀐다.

하네스를 한 문장으로 줄이면, AI가 혼자서도 잘 일할 수 있는 작업 환경이다. 맥락, 제한, 작업 흐름, 검증을 모델 둘레에 두른다. 모델이 엔진이라면 하네스는 그 엔진을 굴러가게 받치는 차체다.

## 여섯 축 한눈에

여섯 축은 일직선이 아니라 순환이다. 구조를 깔고, 맥락을 주고, 계획하고, 실행해서, 검증하고, 개선한다. 그 개선이 다시 구조와 맥락을 바꾼다. 한 바퀴 돌 때마다 모델이 아니라 환경이 조금 더 똑똑해진다.

| 축 | 핵심 질문 | 기억할 한 줄 |
| --- | --- | --- |
| 구조 | 환경을 어떻게 세팅하나 | 폴더 이름이 곧 AI에게 주는 지시다 |
| 맥락 | AI가 무엇을 아는가 | 많이가 아니라, 필요한 때에 정확히 |
| 계획 | 무엇을 어떻게 만들 건가 | "해줘" 대신 "같이 계획하자" |
| 실행 | 누구에게 어떻게 시키나 | 순서면 파이프라인, 독립이면 병렬, 소통이면 팀 |
| 검증 | 결과를 어떻게 믿나 | 만든 AI한테 검사를 맡기지 마라 |
| 개선 | 환경을 어떻게 키우나 | 잘 다듬을수록 단순해진다 |

## 구조: 폴더, 도구, 경계

한 번 잘 깔면 그 위에서 모든 작업이 돌아가는, 가장 오래 가는 투자다.

- **폴더**: 목적이 이름에 드러나게 짠다. `tests/`, `docs/`, `.claude/`. "테스트 작성해줘" 하면 묻지도 않고 `tests`로 간다. 어떤 프로젝트는 폴더만 도메인별로 정리하고 코드는 한 줄도 안 바꿨는데, AI가 그제서야 환불 로직을 `payments/refund/`에 정확히 놓기 시작했다.
- **도구**: 일의 성격에 맞는 자리에 건다. 반복 작업은 Skill, 자동 규칙은 Hook, 일손 추가는 Agent, 바깥 연결은 MCP, 묶어 배포는 Plugin.
- **경계**: 말과 시스템으로 겹쳐서 친다. `CLAUDE.md`에 "main 브랜치 직접 push 금지"라고 적고(말), 동시에 Hook으로 위험한 명령을 강제 차단한다(시스템). 시스템은 깜빡하지 않는다.

## 맥락: 필요한 것을 필요한 때에

맥락은 많이 줄수록 좋은 게 아니다. 천 페이지를 던지면 정작 중요한 정보가 잡다한 것에 묻힌다.

- **상속 3겹**: 유저(`~/.claude/CLAUDE.md`), 프로젝트, 폴더 순으로 좁아지고, 충돌하면 더 가까운 규칙이 이긴다.
- **CLAUDE.md는 가볍게**: 200줄 안팎으로 유지한다. 매 세션 통째로 읽히기 때문에, 다 우겨넣으면 핵심 규칙이 묻힌다.
- **Progressive Disclosure**: 본문은 핵심 30줄만 두고, 두꺼운 규칙은 `rules/`, `references/`로 빼서 glob으로 그 파일을 만질 때만 로드한다. 보안 규칙은 인증 코드 짤 때만, 테스트 규칙은 테스트 짤 때만 들어온다.
- **세션 맥락 비우기**: 대화창이 30~40%를 넘기기 전에 새 세션이나 핸드오프로 옮긴다. 50% 이후 작업은 품질이 떨어져 버리는 셈 치는 게 낫다.

## 계획: "해줘" 대신 "같이 계획하자"

"이거 만들어줘"라고 던지면 AI는 내 머릿속 전제를 모른 채 빈칸을 추측한다. 결과물을 검수하는 왕복이 끝나지 않는다.

- 사람은 자기 전제를 다 말하지 못하니, **방향을 뒤집어 AI가 나에게 되묻게("물어봐") 만든다.**
- 머릿속 계획을 `plan.md` 같은 파일로 꺼낸다. 파일이 되면 검토, 수정, 공유, 재실행, 세션 바뀐 뒤 맥락 복원이 가능해진다.
- 검수 대상이 결과물이 아니라 스펙으로 옮겨가면 고치는 비용이 싸다. 아직 구현을 하나도 안 했으니 한 줄만 바꾸면 된다.
- **계획에서 쓰는 10분이 실행에서 2시간을 아낀다.** 계획은 비용이 아니라 투자다.

## 실행: 싱글, 서브에이전트, 팀

작업 성격에 맞는 실행 패턴을 고르는 일이 오케스트레이션이다.

- **세 패턴**: 혼자 다 하는 싱글, 일을 쪼개 위임하고 종합하는 서브에이전트, 역할끼리 대화하는 팀.
- **고르는 기준**: 순서가 중요하면 파이프라인, 독립적이면 병렬, 소통이 핵심이면 팀.
- **두 개의 숫자**: 일상 작업의 90%는 싱글이나 서브에이전트로 충분하다. 팀 모드는 토큰이 7배까지 뛰니, 여러 관점이 실시간으로 필요할 때만 꺼낸다.
- 서브에이전트는 독립된 컨텍스트에서 일해 메인을 더럽히지 않는다. 무거운 조사는 서브에게 맡기고 메인은 결과만 받는다.
- **자율 루프**: 랄프 루프(완료 기준을 합의하고 충족할 때까지 반복)와 오토리서치(수정, 실행, 평가, 반복)가 극단형이다. 단 기준이 측정 가능해야 루프가 닫힌다.

## 검증: 자신감과 정확성은 따로 논다

AI는 거의 항상 자신 있게 "다 됐습니다"라고 말하지만, 막상 돌리면 안 되어 있는 경우가 많다. 다섯 원칙으로 단단히 한다.

1. **기준을 먼저** 박는다. "잘 되게"가 아니라 "로그인 테스트 통과 + 빌드 성공 + 응답 200ms 이하"처럼 측정 가능하게.
2. **Generator와 Evaluator를 분리**한다. 만든 AI는 같은 맥락에 갇혀 자기 실수를 못 본다. 다른 세션, 다른 컨텍스트의 깐깐한 리뷰어에게 넘긴다.
3. **모델과 역할을 교차**한다. 다른 트레이닝을 거친 다른 두뇌가 맹점을 다른 각도에서 잡는다.
4. **코드만 보지 말고 화면까지** 본다. Browser Agent, Computer Use, 시각 검증 루프. 코드는 멀쩡한데 화면이 깨진 경우가 많다.
5. **되돌릴 수 있는 가드레일**을 둔다. 격리 환경(브랜치, Git Worktree), 위험한 작업의 승인 게이트, dry run. 실수를 0으로 만들기보다 되돌릴 수 있게.

기준 박기와 만든 쪽 · 검사 쪽 분리, 이 둘만 해도 검증의 절반 이상이 잘 된다.

## 개선: 잘 다듬을수록 단순해진다

하네스는 한 번 깔고 끝이 아니라 쓰면서 다듬는 살아 있는 것이다. 그런데 잘 다듬으면 복잡해지는 게 아니라 오히려 단순해진다.

- **관측**: 세션을 분석해 어디서 막히는지 보고, 안 쓰는 코드와 규칙(AI 슬롭)이 쌓이는지 본다.
- **3번의 법칙**: 같은 작업을 3번 했으면 Skill로 굳히고(`/deploy-check`), 같은 실수를 3번 했으면 Rule이나 CLAUDE.md에 못 박는다.
- **덜어내기**: 안 쓰는 건 바로 삭제하고, 모델이 좋아지면 옛 가드레일을 재평가하고, 규칙 파일이 자꾸 길어지면 과설계 신호로 받아들인다.
- 이 루프가 복리(compounding)처럼 쌓인다. 하네스가 필요한 자리는 사라지지 않고, 모델이 못하던 걸 해내면 더 어려운 문제로 옮겨갈 뿐이다.

## 관통하는 한 줄

여섯 축을 다 돌면 한 자리에서 만난다. 좋은 하네스는 더 많은 통제가 아니라, **더 적은 통제로 더 잘 돌아가는 쪽으로 간다.** 에이전트를 처음부터 규칙으로 옥죄지 말고, 자유도를 충분히 준 뒤 안 될 때 하나씩 더하는 게 낫다.

그래서 사람의 역할도 옮겨간다. 코드를 잘 짜는 것에서, AI가 잘 일하는 환경을 설계하는 것으로. 모델이 몇 퍼센트 좋아지기를 기다리는 대신, 오늘 통제권을 쥔 환경을 바꾸는 사람이 되는 것이다.
